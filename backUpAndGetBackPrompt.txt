Set Backup 
----------------------------------------------------------------------

Do the following actions in order:

1. Inspect the current project code before doing anything else:
   - Review the current Prisma schema, migrations, and backup/restore logic.
   - Check whether the existing backup/restore scripts fully cover all current Prisma models/tables and their relations.
   - If the existing scripts are outdated, incomplete, or only handle part of the data, update them first so the backup and restore flow fully supports the current schema.
2. Take a fresh FULL backup of the current local database.
   - The backup must include all current Prisma models/tables in the project, not just a subset.
   - The backup must preserve all rows needed to fully reconstruct the current local database state.
3. Overwrite this exact file with the new backup:
   dbBackupToWork/database_backup.archive
4. Verify the backup before committing:
   - Confirm the generated backup includes every current Prisma model/table that contains application data.
   - If any current table/model is missing from the backup logic, fix the backup logic, regenerate the backup, and use the regenerated file.
5. Create a FULL git commit for the entire project:
   - Include all current changes (code + database backup).
   - Write a clear and meaningful commit message describing the changes.
6. Push the commit to GitHub.

Rules:
- Do NOT compare databases.
- Do NOT merge databases.
- Assume the local database is always correct.
- Always overwrite the existing backup file.
- Treat the local database as the source of truth.
- Ensure the committed backup is compatible with the current Prisma schema and restore flow.
- Do not add explanations.

Get backup From:
----------------------------------------------------------------------

Do the following actions in order:

1. Pull the latest changes from the current GitHub branch.
2. If there are new or updated project dependencies:
   - Install them using the project’s package manager.
3. If Prisma schema or migrations have changed:
   - Apply the required Prisma migrations to the local database.
4. Inspect the current restore logic before restoring.
   - Review the current Prisma schema, migrations, and restore logic.
   - Check whether the existing restore flow fully restores all current Prisma models/tables and their relations from the backup file.
   - If the existing restore logic is outdated, incomplete, or only restores part of the data, update it first and then run the restore.
5. Restore the local database using this exact backup file:
   dbBackupToWork/database_backup.archive
6. Make sure the local database is now fully based on this backup.
   - Restore all current Prisma models/tables present in the backup, not just a subset.
   - If the backup contains data for a current table/model and the restore logic does not restore it, fix the restore logic and run the restore again.
7. Verify the restore result.
   - Confirm the local database now reflects the backup across all current Prisma models/tables included in the backup.
8. Do not create any git commit.
9. Do not push anything.

Rules:
- Assume the backup file is the source of truth.
- Do NOT compare databases.
- Do NOT merge databases.
- Ensure dependency install and Prisma migration steps are completed before restore when required by pulled changes.
- Never use partial backup or partial restore logic when the schema contains additional current tables/models.
- Do NOT add explanations.
